# Plan 16 — Package GitHub Packages npm authentication

## Goal

Package the user's current GitHub Packages npm configuration in every generated environment, materializing `NPM_TOKEN` only on the target in a mode-`0600` `~/.npmrc`. Harden the shared secret-template installer so its default remains compatible with existing callers while permission drift, secret-safe diffing, and temporary-file cleanup are enforced.

## Context

The current `~/.npmrc` is mode `0600` and contains two managed settings: an authentication token for `npm.pkg.github.com` and the `@qawolf` registry mapping. The token must not be copied into Python source or generated bundles.

`GitSetup` already demonstrates the repository's secret-backed single-file pattern: emit a `ConfigFile` containing `${...}` placeholders, call `install_config_template` with an explicit variable whitelist, and declare the keys through `Fragment.secrets`. `render._write_secrets_template()` then emits empty assignments for operators to populate in `~/.config/dotgen/secrets.env`.

The existing `install_config_template` in `src/dotgen/shim.py` is not safe for a materialized npm token: it installs every target as `0644`, prints rendered content through `diff -u`, and does not guarantee cleanup of its rendered temporary file on every error or signal path. Plan 16 fixes that shared boundary before using it for npm authentication.

Plan 14 adds directory vendoring and deterministic config manifests. Plan 16 is additive and must be implemented after Plan 14 or directly on top of its active changes without removing `Fragment.vendors`, `render.config_manifest()`, `install_config_dir`, related tests/fixtures, or combined golden output.

## Scope

- In scope: a dedicated shared `NpmConfig` component; the `NPM_TOKEN` secret registry entry; an exact two-line npmrc template for `npm.pkg.github.com` and the `@qawolf` scope; secure target installation; additive hardening of `install_config_template`; component, registry, shim, snapshot, and manifest coverage; combined Plan 14/15 golden output.
- Out of scope: obtaining, validating, refreshing, or revoking a real GitHub PAT; embedding the current token in source, fixtures, logs, goldens, `dist/`, or archives; changing npm's public registry; adding other organizations/scopes; merging arbitrary pre-existing npmrc entries; changing the sandbox policy that intentionally hides `~/.npmrc`; generalizing modes for non-templated `install_config`; changing Plan 14 vendoring behavior; VM integration coverage or real package-registry requests.

## Steps

1. **Preserve the Plan 14 baseline** — implement against the Plan 14 result rather than restoring affected files from `HEAD`. In particular, retain `Fragment.vendors`, `render.config_manifest()`, `install_config_dir`, the vendoring tests/fixtures, and combined setup/shim goldens. `src/dotgen/fragment.py` and `src/dotgen/render.py` need no Plan 16 logic changes; Plan 16 consumes their existing `ConfigFile.mode`, secret union, build emit, and config-manifest behavior.
2. **Harden secret-template deployment** — change only the existing `install_config_template` area in `src/dotgen/shim.py`, preserving Plan 14's `install_config_dir` and the existing three-argument callers. Define the helper as an isolated subshell function, `install_config_template() (` … `)`, so cleanup and signal traps cannot escape into the component shell. Use `local mode="${4:-0644}"` and reject any value that does not match `0[0-7][0-7][0-7]` before loading secrets or creating a secret-bearing temporary file. Keep the explicit envsubst whitelist and current missing-secret/tool preflight.

   Initialize rendered and staging paths to empty before installing traps. The `EXIT` handler must capture `$?`, clear `EXIT HUP INT TERM`, remove every non-empty temporary path, and exit with the captured status. `HUP`, `INT`, and `TERM` handlers must exit with `129`, `130`, and `143` respectively so the isolated `EXIT` handler performs cleanup. Create the rendered file privately and keep it mode `0600`.

   In diff mode, compare bytes with `cmp -s` and check exact permissions portably with `find "$dst" -prune -perm "$mode" -exec printf x \;`, accepting only the exact output `x`. Report only path-level `NEW` or `CHANGE` metadata when content or permissions drift; never invoke a content-producing diff. In deploy mode, ensure the destination directory exists, create a second temporary file in `dirname "$dst"`, install the rendering into that same-directory staging path with the requested mode, then `mv -f` it over the destination. The isolated cleanup trap owns both temporary files. A failed render or install must leave any pre-existing destination bytes and mode unchanged.
3. **Register the npm credential key** — update `src/dotgen/secrets.py` by adding `NPM_TOKEN` to the closed `SecretKey` registry and a description identifying it as the GitHub Packages npm token. Reuse the existing `Fragment.secrets` union and `_write_secrets_template()` flow so generated templates contain only an empty `NPM_TOKEN=""` assignment.
4. **Add the dedicated npm component** — create `src/dotgen/components/npm_config.py` following the secret-backed `GitSetup` pattern. The component applies to every environment and emits one `ConfigFile` at `npm/npmrc`, itself mode `0600`, containing exactly these managed lines in this order (with a final newline): `//npm.pkg.github.com/:_authToken=${NPM_TOKEN}` and `@qawolf:registry=https://npm.pkg.github.com`. Its setup installs that packaged template to `$HOME/.npmrc` through `install_config_template`, explicitly requests mode `0600`, whitelists only `NPM_TOKEN`, and declares only that secret. No real token is read from the developer's home directory at build time.
5. **Order npm configuration before npm consumers** — update `src/dotgen/registry.py` to import `NpmConfig` and place it in `_SHARED` immediately after `NodeFnm` and before `PiAgent`. This preserves the existing Node bootstrap order, installs `~/.npmrc` before any Pi npm packages are installed, and includes the component in `debian`, `debian-docker`, and `macos` without adding it to `_DOCKER_SKIP`.
6. **Add focused component and registry coverage** — extend `tests/test_components.py` additively, without disturbing Plan 14's vendor tests, to cover the new component's applicability, exact template destination/content/order/final newline, packaged mode, explicit secure setup mode, and `NPM_TOKEN` declaration. Update the environment distribution/order behavior to prove `node_fnm < npm_config < pi_agent` wherever those components exist. Extend `tests/test_secrets_registry.py` to prove each built environment's emitted secrets template includes an empty registered `NPM_TOKEN` entry and that the built npm template still contains the placeholder rather than a rendered value; retain the existing automatic whitelist/registration checks.
7. **Add security regression coverage for the shared helper** — update `_DEF_RE` in `tests/test_shim.py` to recognize both brace-bodied (`name() {`) and subshell-bodied (`name() (`) function definitions while preserving the exact `SHIM_FUNCTIONS` set and cross-OS parity assertions. `install_config_template` does not need to join `_MODE_AWARE`; if it does, adapt `_function_body` to extract a subshell-bodied definition before using it there. Extend the template harness so calls can supply an optional mode, a controlled `TMPDIR`, and fake `envsubst`/`install` executables where required. Cover default `0644` compatibility for the unchanged `GitSetup`-style call, explicit `0600` installation, deploy-time repair of mode drift, read-only diff detection of mode-only drift, invalid-mode rejection before temporary-file creation, and absent targets. For content drift, seed old and new sentinel secret values and assert stdout/stderr contain neither while still reporting only templated path metadata.

   Exercise cleanup after successful deploy, diff return, forced envsubst failure, forced install failure, and `HUP`/`INT`/`TERM`. A forced install failure must preserve the pre-existing destination bytes and mode as well as remove both temporary files. Install sentinel caller traps before success, ordinary failure, and signal cases; assert `trap -p` is byte-identical after the helper returns. For signal coverage, use a blocking fake `envsubst`, wait for a readiness marker, launch the harness with `Popen(..., start_new_session=True)`, and signal only that process group. Every post-creation completion path must leave the controlled temporary locations empty and preserve a nonzero status on failure. Keep OS shim parity/bash-clean coverage and all Plan 14 `install_config_dir` tests intact because the helper lives in `_SHARED`.
8. **Refresh and inspect combined generated expectations** — regenerate `tests/golden/debian/setup.sh`, `tests/golden/debian-docker/setup.sh`, and `tests/golden/macos/setup.sh` for the new `npm_config` component chunk; regenerate all three `os_shim.sh` files for the hardened shared helper; and update the Plan 14 `config-manifest.txt` in each environment with the deterministic mode-`0600` `npm/npmrc` entry. Inspect newly created manifest files directly or with `git diff --no-index /dev/null <file>` until they are tracked; do not assume ordinary `git diff` includes them. `alias.sh` and `.bashrc` should remain byte-identical. Generated `dist/<env>/config/npm/npmrc` should be mode `0600` and placeholder-only, while `dist/<env>/config/dotgen/secrets.env.template` gains `NPM_TOKEN=""`; the latter is intentionally outside `SNAPSHOT_FILES` and `config_manifest()`, so the focused registry test is its guard.

## Data / control flow

`registry._SHARED` selects `NpmConfig` for all three environments after Node setup and before Pi's npm installs. `NpmConfig.render()` returns the mode-`0600` placeholder `ConfigFile`, an `install_config_template` setup action with explicit target mode `0600`, and `Fragment.secrets={NPM_TOKEN}`. The existing fragment merge passes the file and unioned key into the Plan 14 render path: `build_env()` writes `dist/<env>/config/npm/npmrc` without substitution, `config_manifest()` records its mode/hash, and `_write_secrets_template()` emits an empty registry entry.

At deploy or diff time, `install_config_template` loads the target-side secrets file, validates only its declared whitelist, renders into a private temporary file, and compares bytes plus target mode. Diff returns metadata only and cleans the rendering without changing the target. Deploy installs the rendering as `~/.npmrc` mode `0600` and cleans it. Component ordering makes that managed npm configuration available before `PiAgent` invokes `install_npm_global`.

## Decisions

- **Dedicated component.** `NpmConfig` separates credential/config ownership from Node installation and gives registry ordering an explicit npm-consumer boundary. It reuses `GitSetup`, `ConfigFile`, `Fragment.secrets`, and `install_config_template` rather than introducing a new framework.
- **Materialize on target.** The target npmrc contains the token because the shell does not export `secrets.env` for npm processes. The packaged template retains `${NPM_TOKEN}` and the materialized file is restricted to `0600`.
- **Manage the file as an exact replacement.** The current `~/.npmrc` is exactly the two requested lines and already mode `0600`; deployment owns that full file rather than attempting an unsafe merge. Future unrelated npmrc settings require an explicit template change.
- **Metadata-only templated diffs.** All templated configs, including the existing git config, lose unified content diffs. Callers still learn that a path changed, but no rendered secret or neighboring sensitive content is printed.
- **Preserve default compatibility.** Existing three-argument callers continue installing mode `0644`; only `NpmConfig` supplies `0600`. `install_config` and unrelated config modes remain unchanged.
- **Use an isolated subshell and atomic replacement.** Helper traps are scoped by `install_config_template() (` … `)`, staging occurs in the destination directory, and `mv -f` replaces the target only after rendering and installation succeed.
- No unresolved product or architecture decisions remain.

## Risks and non-goals

- Shell signal handling can accidentally leak traps or mask the original exit status. The isolated-subshell contract and caller-trap regression tests are mandatory.
- Exact mode checks must work under both GNU/Linux and macOS/BSD. Use the planned POSIX `find -perm` check rather than platform-specific `stat` flags.
- A real GitHub Packages request is deliberately excluded. Tests cannot prove PAT scopes, SSO authorization, expiration, or private-package access; no test should send the user's token over the network.
- Plan 14 overlaps `src/dotgen/shim.py`, component/shim tests, setup/shim goldens, and config manifests. Apply narrow additive edits and review the combined output rather than restoring files from `HEAD`.
- The existing Debian Docker image runs deployment while building from an empty generated secrets template, so VM coverage would fail before fixture secrets can be injected. Fixing that pre-existing harness limitation is separate work.

## End state

Every generated environment packages a mode-`0600`, placeholder-only GitHub Packages npmrc and an empty `NPM_TOKEN` secrets-template entry. Deployment renders the target's token into an exact mode-`0600` `~/.npmrc` before npm package installation; diff reports content or permission drift without showing secrets; and rendered temporary files survive no success, error, or handled-signal path. Plan 14 vendoring, manifests, tests, and generated behavior remain intact alongside the new component.
